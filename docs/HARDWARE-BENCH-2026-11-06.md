# Orange Pi Zero 3 hardware bench — 2026-11-06

Status: **one-headset partial success (A2DP)**; **HFP voice path blocked**. These are operator-observed tests, not application-level MedveTalkie acceptance.

| Access | Direct Ethernet and SSH; network-interface `end0`, address `192.168.1.200/24` on this temporary bench |

The headless image initially lacked user audio services and `pactl`. Installed `pipewire`, `pipewire-pulse`, `wireplumber`, `libspa-0.2-bluetooth`, `dbus-user-session`, `rtkit`, `pulseaudio-utils` and `sox`. The `medvetalkie` user runs its PipeWire/WirePlumber session using systemd user services and login linger. Without a logged-in local seat, WirePlumber initially did not expose functional Bluetooth media endpoints, causing `br-connection-profile-unavailable`; resolved with:

```ini
# /home/medvetalkie/.config/wireplumber/wireplumber.conf.d/51-bluetooth-headless.conf
wireplumber.profiles = {
  main = {
    monitor.bluez.seat-monitoring = disabled
  }
}
```

After restarting the user's WirePlumber, Bluetooth connection succeeded. For a production daemon, revisit permissions, headless lifecycle and profile stability.

## SCO HCI evidence

Captured with `btmon -w /tmp/airide-hfp.btsnoop` during HFP playback:

```text
Setup Synchronous Connection: Command Status Success (0x00)
Synchronous Connect Complete: Status Success (0x00)
Link type: eSCO (0x02)
Handle: 3584
TX packet length: 60
RX packet length: 60
Air mode: Transparent (0x03)
SCO Data TX: 595 packets
SCO Data RX: 0 packets
```

Cumulative HCI counters at later inspection:

```text
RX sco:0
TX sco:9168
RX errors:0
TX errors:0
```

The monitor proves HCI SCO payloads were **submitted outbound**, not that the headset received intelligible audio. Zero incoming SCO packets establishes the microphone path is unavailable at host HCI; it does **not alone** explain silent speaker playback. `hciconfig hci0 voice` was `0x0060` (linear 16-bit host input and CVSD air coding default); avoid inferring negotiated mSBC settings from this default.

## Driver and firmware audit

Current Armbian module:
`/lib/modules/6.18.60-current-sunxi64/kernel/drivers/net/wireless/uwe5622/tty-sdio/sprdbt_tty.ko`.
Observed module symbols/strings include `mtty_rx_cb`, `mtty_rx_task`, `mtty_tx_cb`, `mtty_write`, `parse_frame`. The exact *built* source commit and binary/source correspondence remain **unverified**.

Reference upstream: https://github.com/armbian/uwe5622/tree/master/tty-sdio

Static source inspection:

- `tty-sdio/tty.c:mtty_rx_cb` feeds received SDIO payload into `tty_insert_flip_string`. There is no explicit incoming-HCI-SCO filter in this function.
- Its overflow path reuses `head` as an owned queued buffer and replaces `head->buf` before returning `head` to the bus pool: unsafe buffer ownership, independently deserving a fix.
- The queued RX worker has an unbounded busy retry if `tty_insert_flip_char` cannot accept a byte.
- `tty-sdio/alignment/sitm.c` recognizes HCI type `0x03` for *outgoing* SCO packets and frames TX; it does not prove inbound SCO is delivered.
- Whether WCN firmware emits SCO via SDIO/HCI or routes voice elsewhere (e.g. dedicated PCM) is still **unknown**; do not assert a root cause without counters at the actual SDIO receive callback.

Related project: https://github.com/Medvedolog/opiz3-wlan-backport — its OpenWrt package builds WCN BSP/Wi-Fi modules, **not** `sprdbt_tty`. Its firmware package SHA-256 matches this bench's active `wcnmodem.bin`. Historical WLAN patches must not be treated as Bluetooth fixes.

An alternative `wcnmodem-38222.bin` (~1.7 MiB vs ~925 KiB active firmware) was found, but device compatibility and purpose are **unverified**. **Do not substitute firmware blindly.** There is no evidence to change the working 1500000 attach rate either.

## Next controlled experiments

1. Identify exact Armbian UWE5622 build revision matching installed kernel; pin and diff source.
2. Add opt-in counters at `mtty_rx_cb` to count incoming SDIO frames by HCI packet type, plus short TTY insertions, queue depth and drops. Do not print packets continuously to console.
3. Run HFP test, compare SDIO HCI type 0x03 with `hciconfig` SCO RX and `btmon`.
4. If SCO reaches SDIO but not HCI, debug driver framing and TTY backpressure. If none reaches SDIO, inspect WCN voice routing/vendor initialization.
5. Separately fix the RX queue buffer lifetime and bounded retry behavior; regression test A2DP and pairing.
6. Test AIRIDE N1 on independent USB BT HFP controller with the *same* user stack, then attempt two simultaneous independent HFP links.
7. Confirm stability, Wi-Fi coexistence, CPU/RAM, power and audio latency before promoting MedveTalkie full-duplex claims.

## Test artifacts and operational safeguards

Runtime trace on the SBC: `/tmp/airide-hfp.btsnoop` (not checked into Git; may contain device identifiers and payload). WAV test files `/tmp/airide-tone.wav`, `/tmp/airide-test.wav` are also local. PipeWire node IDs are ephemeral: use `bluez_output.41_42_63_27_E7_3A.1` rather than a numeric `--target` identifier where possible. Do not conflate `SUSPENDED` idle nodes with HFP failure.

This is a **hardware feasibility finding**, not a fixed driver, not a full-duplex demonstration and not evidence of two-controller capability.
