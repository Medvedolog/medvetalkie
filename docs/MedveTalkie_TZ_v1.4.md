# MedveTalkie Intercom

**Техническое задание — версия 1.4 (проект, 06.11.2026)**  
**Платформа:** Orange Pi Zero 3 (Allwinner H618), Armbian Debian 13 ARM64  
**Основной сценарий:** двусторонняя связь двух пользователей с универсальными Bluetooth-гарнитурами; пассажир сзади или отдельный велосипед/самокат. Дополнительный сценарий: одиночная поездка с Android-смартфоном вместо второго участника.  
**Состояние:** концепция и план испытаний; работоспособность HFP/SCO на выбранном железе ещё не подтверждена.

## 1. Цель

Создать автономный Bluetooth-интерком для двух гарнитур с постоянным полным дуплексом, автоматическим подключением и восстановлением связи. Дополнительно — SPI-дисплей, GPIO-кнопки, голосовые уведомления и управление, эфирное и интернет-радио, эмуляторы ретроигр с HDMI, независимая маршрутизация аудио.

**Главный принцип:** в режиме INTERCOM голосовая связь имеет абсолютный приоритет. В режимах SOLO_STEREO и ANDROID_BRIDGE микрофон и Bluetooth-профили управляются отдельно; пользователь явно уведомляется о переключении и временной недоступности микрофона. Радио, игры, AP и веб-интерфейс не должны нарушать текущий активный голосовой маршрут.

## 3. ПО и отправные точки

- **ОС:** Armbian Debian 13 Minimal CLI, ARM64. Страница образов: https://www.armbian.com/boards/orangepizero3/
- **Bluetooth:** BlueZ, D-Bus; звуковые профили HFP/HSP через совместимый стек PipeWire/WirePlumber.
- **Аудио:** PipeWire + WirePlumber; устойчивые виртуальные узлы, микширование и маршрутизация.
- **Интерком-референс:** https://github.com/phieri/bt-intercom
- **Голосовые уведомления:** RHVoice (локально, русский язык).
- **Распознавание команд:** Vosk, компактная русская модель (локально, ограниченная грамматика).
- **FM:** съёмный ATS Mini V4; аналоговый стереозвук в USB Line-In; штатный RDS читается на экране приёмника. USB Serial/BLE управление и экспорт RDS — отдельные необязательные этапы.
- **Ретроигры:** RetroArch + Libretro (Genesis Plus GX, Snes9x, FinalBurn Neo); для меню — EmulationStation/ES-DE при подтверждённой графической поддержке ARM64/H618.
- **Референс для игр на Orange Pi Zero 3:** https://github.com/onex01/OrionOS
- **Дисплей:** Linux spidev + библиотека отрисовки (на MVP — Python/Pillow или C/Rust), без X11/Wayland ради одного SPI-экрана.
- **GPIO:** libgpiod, Device Tree Overlay, проверка фактической распиновки.

**Юридическое ограничение:** лицензия `phieri/bt-intercom` должна быть проверена до заимствования или распространения производного кода. Не предполагать, что доступность GitHub-исходников автоматически разрешает перепубликацию.

## 4. Критически важная проверка осуществимости

До разработки оболочки выполнить измерения на реальном стенде:

1. Встроенный BT AW859A определяется в Armbian и работает с тестовой гарнитурой №1 (Airide N1).
2. Тестовая гарнитура №2 (Honor) подключается со своим микрофоном через HFP/HSP.
3. Два HFP/SCO/eSCO-соединения работают **одновременно**; если нужно — на отдельных контроллерах.
4. В обе стороны передаётся звук без нажатия PTT, без самопрослушивания и устойчиво к переподключениям.
5. Команды кнопок каждой гарнитуры проверяются через AVRCP/HFP/evdev; работа долгого нажатия не предполагается без проверки.
6. Аудиотракт не разваливается при старте сетевых и графических служб.

**Критерий Go/No-Go:** реальный полнодуплексный разговор двух гарнитур. При провале данного теста не позиционировать проект как готовый интерком.

## 5. Базовые режимы

- **INTERCOM:** всегда открыты оба микрофона; двустороннее соединение.
- **PHONE_DIRECT:** совместимость со старым режимом: Orange Pi отпускает гарнитуру №1, чтобы Android связался с ней напрямую; звуковой мост на Pi отключён.
- **SOLO_STEREO:** одна гарнитура №1 в A2DP, микрофон гарнитуры на Pi не используется; FM/игры/сетевое аудио передаются стерео.
- **ANDROID_BRIDGE:** гарнитура №1 подключена к Pi, Android подключён через второй BT-контроллер: музыка/навигация Android → Pi A2DP Sink → гарнитура A2DP Source; звонки — отдельный экспериментальный маршрут HFP HF↔AG с переключением гарнитуры в HFP.
- **ANDROID_MEDIA:** частичный подрежим ANDROID_BRIDGE: музыка и навигация без телефонной разговорной функции; первая реализация.
- **PAIRING:** явная команда, ограниченное время обнаружения, сохранение доверенных устройств по MAC, никакого автоматического доверия чужим гарнитурам.
- **DEGRADED:** одна гарнитура отсутствует или HFP недоступен; оповестить доступного участника и восстанавливать соединение без спама.
- **RADIO:** поверх интеркома работает эфирное либо интернет-радио.
- **GAME:** радио по умолчанию останавливается; запускаются RetroArch и меню ROM на HDMI (или экспериментально SPI), а интерком продолжает работать.

## 6. Единая аудиоматрица — ключевое дополнение версии 1.1

### 6.1. Входные потоки

- `HEADSET_1_MIC` — голос пользователя 1 (доступен только в HFP/HSP).
- `HEADSET_2_MIC` — голос пользователя 2 (доступен только в HFP/HSP).
- `FM_AUDIO` — стерео PCM из USB Line-In от ATS Mini V4 (без обязательной модификации радиоприёмника).
- `NET_RADIO` — интернет-радио через Wi-Fi телефона / USB LTE-модем.
- `GAME_AUDIO` — звук RetroArch.
- `ANDROID_MEDIA_IN` — A2DP-поток от Android к Orange Pi (Pi — A2DP Sink).
- `ANDROID_CALL_DOWNLINK` / `ANDROID_CALL_UPLINK` — экспериментальный двусторонний телефонный поток при поддержке HFP HF на Pi.
- `TTS` — уведомления и ответы локального голосового помощника.

### 6.2. Выходные потоки

- `HEADSET_1_OUT` — **голос пользователя 2 + (FM/интернет-радио/игра) + адресные уведомления** в INTERCOM; качественное A2DP-стерео в SOLO_STEREO и ANDROID_MEDIA.
- `HEADSET_2_OUT` — **голос пользователя 1 + адресные уведомления**, медиа по умолчанию не подмешивается.
- `HDMI_OUT` — **стереозвук FM или игры**, но не приватные разговоры по умолчанию.
- `SPEAKER_OUT` — по выбору служебные звуки, радио либо игра во встроенном динамике.

### 6.3. Режимы аудио

| Источник | INTERCOM | RADIO | GAME |
|---|---|---|---|
| Двусторонний разговор | Да | Да | Да |
| Эфирное/интернет-радио | Нет | Да | Нет |
| Звук RetroArch | Нет | Нет | Да |
| FM/игра в гарнитуре №1 | Нет | Да | Да |
| FM/игра по HDMI | Нет | По выбору | Да |
| Радио в гарнитуре №2 | Нет | Нет по умолчанию | Нет |
| Голосовые уведомления | Да | Да | Да |

**Взаимоисключение:** запуск GAME выключает RADIO; запуск RADIO прекращает GAME_AUDIO либо требует явного подтверждения закрытия игры. В INTERCOM сохранять разговор. В SOLO_STEREO и ANDROID_MEDIA переключение HFP↔A2DP выполняется явной транзакцией с обратным откатом при ошибке.

### 6.4. Приоритеты и микширование

1. Разговор с ребёнком всегда различим на фоне медиазвука.
2. Детектор речевой активности (VAD) временно приглушает радио/игру ориентировочно на 12–18 дБ, с плавной атакой и отпусканием; параметры настраиваемые.
3. Уведомления адресуются конкретному пользователю и не должны чрезмерно перекрывать чужую речь.
4. Громкость гарнитур №1/№2, HDMI, встроенного динамика и медиапотока регулируется независимо.
5. Для детского выхода — отдельный верхний предел уровня; общий регулятор его не отменяет.
6. При переподключении использовать устойчивые device IDs/сопоставление по свойствам, а не закодированные номера `wpctl`.
7. Потеря HDMI не должна вызывать сбой Bluetooth-аудио.
8. По умолчанию не выводить микрофоны в HDMI или внешний динамик (приватность, акустическая обратная связь).

### 6.5. HFP ↔ A2DP и осознанное отключение микрофона

В стандартной Bluetooth Classic гарнитуре HFP/HSP обеспечивает двусторонний монофонический голос (CVSD/mSBC), а A2DP — качественный стереопоток **без микрофона гарнитуры**. Одновременность HFP и A2DP на одной гарнитуре не предполагается. При выборе SOLO_STEREO приложение освобождает HFP-аудиотракт, активирует A2DP и показывает `Микрофон выключен (A2DP)`. При возврате в INTERCOM восстанавливает HFP, микрофон и аудиомаршруты, подтверждает готовность. Никакой автоматической незаметной потери микрофона. При звонке Android в режиме ANDROID_BRIDGE можно временно переключить гарнитуру в HFP и после завершения вернуть A2DP.

Смартфон и гарнитура имеют разные роли: для Android Orange Pi — **A2DP Sink** (получатель музыки) и, для звонков, **HFP Hands-Free**; для гарнитуры Orange Pi — **A2DP Source** либо **HFP Audio Gateway**. Проверить поддержку и совместимость противоположных HFP-ролей в BlueZ/PipeWire/oFono/hsphfpd на выбранном образе; считать звонки и голосовые помощники через HFP *экспериментальными* до реального теста, а не обещанной функцией.

## 7. FM: ATS Mini V4 и интернет-радио

### 7.1. Съёмный ATS Mini V4 — базовый путь

- Готовый ATS Mini V4 на ESP32-S3 + Si4732 с собственным экраном, RDS и аккумулятором, без обязательной перепрошивки или пайки.
- Штатный выход 3,5 мм → **стерео** USB-аудиоинтерфейс с настоящим линейным входом (не монофонический микрофонный адаптер) → PipeWire → выбранные выходы, включая HDMI.
- Для USB-C предусмотреть короткий гибкий кабель (питание/заряд/опциональное управление), возможность его отключить при цифровом шуме в аналоговом тракте; избегать жёсткой стыковки двумя разъёмами одновременно.
- Частота и RDS на штатном экране ATS Mini — достаточны для MVP; экспорт RDS в MedveTalkie **не обязателен**. При необходимости отдельным этапом USB Serial либо BLE управление без вмешательства в аудиоподсистему.
- Док разъёмный, с доступом к антенне, механической фиксацией от вибраций и самостоятельной работой извлечённого приёмника.
- Возможная оцифровка через I²S/USB Audio в будущем — исследовательский этап, не блокирующий основную функциональность.

### 7.2. Интернет-радио

Ethernet, Wi-Fi-клиент, USB LTE или смартфонный источник. Интернет не требуется для базовой голосовой связи. При исчезновении сети прекращается только сетевой медиапоток.

## 8. HDMI, SPI и эмуляторы

- **HDMI:** RetroArch + графическое меню выбора ROM. Игровое видео и основной стереозвук на HDMI.
- **SPI:** дисплей MSP2008 (ST7789) постоянно показывает заряд/соединения, режим, радио, IP, состояние игры; возможен отдельный экспериментальный вывод игр 320×240 с ограниченной частотой кадров.
- **Контроллер:** Bluetooth-геймпад (проверить сосуществование с HFP) либо USB-геймпад.
- **ROM:** на карте microSD, например `/srv/medvetalkie/roms/{megadrive,snes,neogeo,nes,gba}`. Законно полученные образы; совместимый BIOS для Neo Geo при необходимости.
- **Запуск GAME:** включить HDMI-вывод/меню, приостановить радио, сохранить интерком и мониторинг батарей.
- **Выход GAME:** закрыть проигрыватель и вернуть исходную конфигурацию аудиоматрицы.

## 9. Дисплей, кнопки, статусы

Основной экран MSP2008 в альбомной ориентации 320×240:

- Гарнитура №1: связь, батарея (если сообщает), качество BT (если доступно), громкость и профиль HFP/A2DP.
- Гарнитура №2 или Android: аналогичные поля с учётом типа устройства и профиля.
- Режим: INTERCOM / SOLO_STEREO / ANDROID_MEDIA / ANDROID_BRIDGE_CALL / PHONE_DIRECT / PAIRING / RADIO / GAME; режимы работы аудио и приложения отображаются отдельно.
- Интернет: Wi-Fi / LTE / отсутствует.
- FM-частота и RDS, только если доступны по USB/BLE от ATS Mini (иначе смотреть его собственный экран); интернет-радио и текущая игра — по контексту.
- Отдельный индикатор критических ошибок, низкого заряда и состояния голосового канала.

**Кнопки:** цифровой 5-позиционный джойстик (слева) + четыре игровые/контекстные кнопки (справа); опционально отдельная системная кнопка. Доступ к физическим кнопкам через GPIO/libgpiod или MCP23017 I²C, единый слой ввода → evdev/uinput для RetroArch; без аналогового KY-023, если нет АЦП. GPIO и SPI-пины подтвердить по DT/ревизии, 5 В к GPIO не подключать. На мотоцикле исключить необходимость чтения сложных меню в движении.

## 10. Управление Bluetooth, сопряжение и кнопки гарнитур

При включении Orange Pi ищет заранее сохранённые гарнитуры и восстанавливает подключение. Для известных устройств выполняется `connect`, а не повторный `pair` на каждом старте. Логические роли `HEADSET_1`, `HEADSET_2`, `PHONE_1` и `BT_CONTROLLER_A/B` закреплять по устойчивым D-Bus и sysfs/udev признакам, MAC/физическому USB-пути и существующим bond; номера `hci0/hci1`, Bus/Device и PipeWire numeric IDs не считать стабильными. Отдельное USB-устройство не получает ключи сопряжения автоматически от старого адаптера; смена контроллера требует отдельной процедуры переноса или повторного pairing. Предотвращать конфликт назначения одного физического контроллера нескольким несовместимым ролям.

Предлагаемые действия:

| Жест | Назначение | Статус |
|---|---|---|
| Короткая системная кнопка | INTERCOM ↔ SOLO_STEREO (подтверждение потери микрофона) | Проектируется |
| Удержание ~3 с | Переподключить известные гарнитуры | Проектируется |
| Удержание ~7 с | Открыть окно сопряжения ~60 с | Проектируется |
| Кнопки громкости гарнитуры №1 | Громкость её выхода без обхода лимита пользователя №2 | Только если события доступны Linux |
| Пять нажатий гарнитуры №1 | Озвучить заряд обоих устройств | Только если события доступны Linux |
| Удержание гарнитуры №1 | Активировать голосовое управление | Только если событие передаётся |

**Примечание:** кнопка переводит Orange Pi в режим поиска, но сама по себе не переводит гарнитуру в pairing. Телефон может удерживать соединение и мешать возвращению гарнитуры к Pi. Реакция на AVRCP/кнопки тестируется для каждой модели отдельно, включая во время активного HFP.

## 11. Голосовые оповещения и помощник

- RHVoice — офлайн-озвучивание подключения, потери и восстановления связи, низкого заряда, ошибок сети и радио, готовности устройства.
- Vosk — распознавание ограниченного перечня русских команд после нажатия/удержания кнопки.
- Пример команд: «Сколько времени?», «Какой заряд гарнитур?», «Включи радио», «Выключи радио», «Следующая станция», «Сделай тише», «Как работает связь?».
- Во время команды микрофон N1 временно изолируется от второго участника; голос ребёнка по возможности остаётся слышен водителю.
- Предупреждение о слабой связи — не по одиночному RSSI, а по устойчивому ухудшению/обрывам, с гистерезисом и защитой от повторения.
- Уровень заряда получать только из фактической телеметрии BlueZ/HFP/Battery1. При отсутствии данных озвучивать «Заряд неизвестен».
- Не делать постоянную запись разговоров и не выполнять произвольные shell-команды из распознанной речи.

## 12. Встроенный динамик и аналоговое аудио

В корпусе разместить небольшой динамик (ориентир 28–40 мм) и мини-усилитель класса D, например PAM8302A. Аналоговый line-out Orange Pi нельзя напрямую нагружать динамиком. Для монофонического выхода смешивать L/R **программно**, не замыкать два линейных выхода друг на друга. При возможности предусмотреть аппаратное отключение усилителя для исключения фона и акустической обратной связи.

Работу аналогового кодека на выбранном ядре Armbian подтвердить командами `aplay -l`, `cat /proc/asound/cards` и тестовым сигналом: отсутствие разъёма 3,5 мм на основной плате не означает отсутствия аппаратного аналогового выхода, но поддержка в конкретном Linux-образе может отличаться.

## 13. Надёжность и безопасность

- Интерком — отдельная служба systemd с управляемым перезапуском.
- При сбоях радио, SDL/RetroArch, HDMI или дисплея интерком не перезапускается.
- При потере гарнитуры — ограниченные повторные подключения с backoff и голосовым оповещением доступного участника.
- Защита от циклического переподключения и дублирования PipeWire-маршрутов.
- Управление без экрана и интернета.
- Независимый лимит громкости гарнитуры №2; для реальной езды проверить детское размещение наушника, не нарушающее защитную посадку шлема и слышимость дорожной обстановки.
- Никаких действий с экраном/меню при движении: кнопки и голосовой интерфейс должны позволять работать вслепую.
- Влажность, вибрации, охлаждение, крепление аккумулятора и электрозащита входят в проверку корпуса.

## 14. Этапы работ

1. **M0 — аппаратный HFP:** Armbian, два контроллера, две гарнитуры, полный дуплекс, измерение задержки и стабильности.
2. **M1 — базовый MedveTalkie:** автоподключение, восстановление, регулировка громкости, логические роли вместо hciN и USB Bus/Device.
3. **M2 — UI:** MSP2008, цифровой джойстик + четыре кнопки, индикация заряда/профиля, съёмный док ATS Mini V4.
4. **M3 — голос:** RHVoice, обработка кнопок N1, Vosk, уведомления.
5. **M4 — аудиоматрица:** независимые выходы, VAD-приглушение, HDMI, встроенный динамик.
6. **M5 — FM/интернет-радио:** ATS Mini V4 + стерео USB Line-In, проверка шума, аудиовывод по HDMI/A2DP, RDS на собственном экране.
7. **M6 — ретроигры:** RetroArch, Libretro, ROM-библиотека на карте, BT/USB-геймпад, HDMI; взаимное исключение GAME и RADIO.
8. **M7 — тестирование:** двухчасовой разговор, 10 перезапусков с перенумерацией USB, нагрузка ATS Mini + HFP + HDMI + AP, оценка температуры/питания.
9. **M8 — стерео и Android:** SOLO_STEREO → ANDROID_MEDIA → экспериментальный ANDROID_BRIDGE для звонков.
10. **M9 — Web/AP/STA:** защищённая локальная панель, запуск AP с IPS и QR для смартфона, Wi-Fi-клиент 5 ГГц для интернет-радио, проверка совместимости Wi-Fi/Bluetooth; миграция патчей AW859A/UWE5622 из opiz3-wlan-backport.

## 15. Критерии приёмки

- Двусторонний разговор обоих пользователей без переключения PTT и без самопрослушивания.
- Подключение известных устройств автоматически, без повторного сопряжения после перезагрузки.
- Утрата связи с одной гарнитурой не вызывает зависания второй и остальных служб.
- Радио можно слушать в гарнитуре №1 **одновременно** с разговором в HFP-качестве; в SOLO_STEREO — качественное A2DP-стерео при явно отключённом микрофоне.
- Звук игры и/или радио можно направить на HDMI при сохранении звука разговора в HFP-гарнитурах; приватные микрофоны не выводятся на HDMI по умолчанию.
- При речи ребёнка музыка/игра приглушается, но не заглушается голос собеседника.
- Детская громкость ограничивается независимо от общей регулировки.
- Встроенный динамик, экран, голосовое управление, сеть и HDMI могут быть недоступны без потери базовой функции интеркома.
- Все аппаратно-зависимые функции (RSSI, заряд, AVRCP, аналоговый звук, HDMI на выбранном ядре) отмечены как проверенные только после натурного теста.

## 16. Основные риски

| Риск | Следствие | Решение |
|---|---|---|
| SCO/HFP не работает на встроенном BT | Нет базового аудиоканала | Совместимые USB BT-контроллеры |
| Кнопки гарнитуры не передаются на Linux | Нет жестов/удержания | Кнопки на корпусе или руле |
| Гарнитура занята телефоном | Pi не подключает её автоматически | Явный PHONE_DIRECT/INTERCOM; освобождение с телефона |
| HFP-качество для игр/радио | Звук в шлеме «телефонный» | Явно переключать SOLO_STEREO/A2DP с отключением микрофона; при INTERCOM сохранять HFP |
| ATS Mini + USB Line-In + BT + AP нагружают USB/радиотракт | Шумы, обрывы, просадки питания | Короткие экранированные кабели, питание, USB autosuspend, разнос антенн, нагрузочные тесты |
| Драйвер SPI/HDMI несовместим с ядром | Нет изображения | Фиксация проверенного ядра; отдельные тесты DRM/KMS и SPI |
| Отсутствует телеметрия гарнитур | Нет процентов/RSSI | Показывать «нет данных», не подменять оценками |
| Лицензии сторонних репозиториев и моделей | Ограничения публикации | Правовая проверка, разрешения либо самостоятельный код |

---

**Результат:** автономный MedveTalkie Intercom с постоянной двусторонней Bluetooth-связью, экраном MSP2008, физическим управлением и голосовыми функциями. FM/интернет-радио и ретроигры — дополнительные источники звука, которые микшируются с разговором через PipeWire и могут выводиться на HDMI без нарушения приоритета основного голосового канала.


## 17. Режимы одной гарнитуры и Android-смартфона (новое в v1.2)

**Сценарий:** один водитель, гарнитура №1 закреплена за Orange Pi, слот второго участника переиспользован для Android-телефона. При возврате пассажира приложение должно освобождать телефонный маршрут, не удаляя долговременное сопряжение Android.

| Режим | BT-гарнитура №1 ↔ Pi | Android ↔ Pi | Микрофон шлема | Приоритет / статус |
|---|---|---|---|---|
| `INTERCOM` | HFP AG↔HF | Нет | Да | Два двусторонних HFP-канала с пользователями 1/2; главный режим |
| `SOLO_STEREO` | A2DP Source→Sink | Нет | **Нет** | Стерео FM/интернет-радио/игры |
| `ANDROID_MEDIA` | A2DP Source→Sink | A2DP Sink←Source | **Нет** | Android-музыка/навигация; первый Android MVP |
| `ANDROID_BRIDGE_CALL` | HFP AG↔HF | HFP HF↔AG | Да | Двусторонний звонок и голосовой помощник Android — **эксперимент**, нужны оба HFP-стека и маршруты |
| `PHONE_DIRECT` | Отпустить гарнитуру №1 | Android ↔ гарнитура напрямую | Зависит от телефона | Надёжный резерв, без звукового посредничества Pi |

**Термины:** Pi должен поддерживать роли **A2DP Sink от Android** и **A2DP Source к гарнитуре**. Для звонков — роли **HFP Hands-Free к Android** и **HFP Audio Gateway к гарнитуре**. Поддержка профилей на уровне BlueZ не является доказательством работающего HFP relay: возможны несовместимости HFP-backend (oFono/hsphfpd/native), управления звонком, SCO/PCM, кодеков и AVRCP. Мультипрофильный Bluetooth-канал телефона может создавать конкуренцию с A2DP при вызове; нужна диагностика профилей и автоматика отката.

**Звуковая логика:** Android A2DP → захват PipeWire → микшер с FM (по пользовательской политике; по умолчанию музыка Android приоритетнее FM) → гарнитура A2DP. На время звонка отключить/приостановить медиа, переключить гарнитуру на HFP, направить `HEADSET_1_MIC → ANDROID_CALL_UPLINK`, `ANDROID_CALL_DOWNLINK → HEADSET_1_OUT`, защитить от петли и самопрослушивания, после вызова восстановить ранее выбранный профиль/громкость. Навигационные подсказки могут поступать через A2DP и/или SCO/HFP по политике Android; режим, который конкретный телефон выбирает для Google Maps/Яндекс Навигатора/ассистента, определяется практическим тестом. **Нельзя обещать работу Android Assistant/Google Assistant только по факту A2DP-соединения**: для голосовых команд через микрофон шлема необходим фактически работающий двусторонний HFP-мост.

**Управление:** обнаружение Android в веб-панели и на IPS-дисплее; явное сопряжение, выбор режимов, запрет автоматического захвата телефона при `INTERCOM`, сохранение приоритетов, ограниченное переподключение. Никакого автоматического подключения к посторонним смартфонам.

## 18. Wi-Fi AP и локальная веб-панель (новое в v1.2)

### 18.1. Доступ с Android без внешнего интернета

- Режим точки доступа `MedveTalkie-XXXX` с уникальным на устройстве SSID и случайным WPA2/WPA3 паролем; *никаких* общих заводских секретов. Для совместимости разрешён WPA2-PSK/AES. Пароль отображать на IPS при первичной настройке или предоставлять защищённо владельцу при физическом действии; не показывать постоянно прохожим.
- Предлагаемый адрес AP-интерфейса `192.168.47.1/24`, DHCP `192.168.47.100–199`. HTTP(S)-панель: `http://192.168.47.1/` для изолированного MVP; целевой HTTPS с локальным сертификатом / доверенным доступом при удалённом управлении. Домен `medvetalkie.local` через mDNS опционально; IP остаётся запасным вариантом.
- Службы: `hostapd` + `dnsmasq` или `NetworkManager` (один выбранный менеджер без конкурирующей настройки интерфейса); небольшой backend (например FastAPI/Flask, либо Go/Rust), локальный JSON API + SSE/WebSocket для состояний. Веб-сервис **не выполняет shell-команды из запросов**: взаимодействует с контроллером MedveTalkie через строго определённое IPC/D-Bus API.
- **Ключевое ограничение AW859A:** встроенный комбинированный Wi-Fi 2,4/5 ГГц + Bluetooth использует общие аппаратные ресурсы. Режим STA на 5 ГГц подтверждён пользователем на OpenWrt, но переносимость и сосуществование с HFP в Armbian требуется проверить. Для интернет-радио выбирать 5 ГГц STA как предпочтительный режим. Если AP/HFP конфликтуют, приоритет остаётся у переговорки; альтернативой является отдельный USB Wi-Fi-адаптер.
- Телефон при подключении к AP может потерять доступ к мобильному интернету или отказаться от локальной сети без выхода в интернет; интерфейс должен работать offline. Если Android должен одновременно слать музыку/навигацию через BT и открывать веб-панель по Wi-Fi — проверить совместимость конкретного телефона. Никакой обязательной маршрутизации мобильного интернета через Pi.

### 18.2. Страницы веб-интерфейса

| Страница | Содержимое / действия |
|---|---|
| **Обзор** | Режим, две логические роли гарнитур или гарнитура+Android, активные HFP/A2DP, микрофоны ВКЛ/ВЫКЛ, уровень звука, FM, USB/BT/AP, сообщения об ошибках и время последнего изменения |
| **Режимы** | Крупные переключатели INTERCOM, SOLO_STEREO, ANDROID_MEDIA, ANDROID_BRIDGE_CALL (эксперимент), PHONE_DIRECT; предпросмотр последствий и подтверждение выключения микрофона |
| **Bluetooth** | Список контроллеров с устойчивыми ID, фактическими `hciN`, привязанные устройства, pairing с ограниченным временем, connect/disconnect, диагностика HFP/SCO, A2DP и батарей |
| **Аудио** | Источники/выходы, независимые громкости, детский лимит, ducking/VAD, HDMI, тестовый сигнал, индикаторы ошибок маршрутизации; живые статусы, без автоматического воспроизведения звука на максимуме |
| **FM и медиа** | Наличие USB Line-In/ATS Mini, микшер FM, выключатель радио, необязательное переключение станций при наличии подтверждённого USB/BLE управления; индикация RDS на собственном дисплее ATS Mini достаточна |
| **Система** | AP параметры, имя устройства, версия ядра/BlueZ/PipeWire, журналы с фильтрацией, экспорт диагностического архива без персональных данных и секретов, обновления и резервирование конфигурации |

Мобильная адаптивная страница для Android, без внешних CDN, аккаунтов и зависимости от интернета. На статической главной странице — краткая панель состояния и большие режимные кнопки; расширенная диагностика — во вторичных разделах. Изменения через API подтверждаются только после ответа реальной подсистемы, не оптимистически. Каждая операция имеет тайм-аут, откат, журнал, блокировку конкурентных переходов и объяснение ошибки. Управление сопряжением, смена аудиопрофилей и перезапуск служб доступны только владельцу после аутентификации.

### 18.3. Безопасность и условия движения

- AP изолирован от LAN/интернета по умолчанию: нет открытого SSH, форвардинга и гостевого управления. Веб-панель ограничена AP-интерфейсом/локальным сокетом; серверный доступ только авторизованным пользователям. CSRF-защита, HTTP-only cookie, ограничение попыток входа, проверка прав и входных данных.
- Первичное администрирование только после физического подтверждения кнопкой на корпусе либо одноразового кода на экране. Отдельный пароль панели, не равный Wi-Fi PSK; если HTTP используется на MVP — не считать его безопасным при доступе недоверенных клиентов, предпочесть HTTPS на этапе эксплуатации.
- При движении Web UI — преимущественно **просмотр состояния**: изменение сложных настроек и сопряжение предназначены для остановки. Не рассчитывать на автоматическое распознавание движения как единственную меру защиты. Все основные действия доступны без смартфона.

### 18.4. Управляющее состояние и устойчивость

- Источник истины — локальная конфигурация MedveTalkie + фактическое состояние BlueZ/PipeWire; веб-панель только клиент. `mode_requested`, `mode_effective`, `transition_state`, `error`, `revision`, `last_changed` хранить раздельно.
- Критический intercom-service работает независимо от веб-сервера, AP, ATS Mini, HDMI и RetroArch. Отключение браузера не влияет на аудио. Состояние устройства выводится на SPI-экран и дублируется в веб-UI.
- Отслеживать USB-устройства по физическому пути/MAC/сопряжениям; при неопределённости маркировать роль как требующую назначения, а не автоматически переставлять пары.

## 19. Приёмочные испытания v1.2

1. **Bluetooth MVP:** HFP-гарнитура №1 работает со своим микрофоном; по возможности две гарнитуры в независимом полном дуплексе минимум 2 часа, с фиксированием числа рабочих SCO/eSCO каналов.
2. **Стерео:** в SOLO_STEREO гарнитура получает A2DP с FM и/или тестовым файлом; микрофон корректно обозначен выключенным; возвращение в HFP восстанавливает голос без перепаривания.
3. **Android media:** Android сопрягается со вторым контроллером, передаёт музыку и навигационные подсказки через Pi в гарнитуру №1 по A2DP; задержка, обрывы, переключения и экранирование фиксируются.
4. **Android call (отдельный экспериментальный gate):** входящий/исходящий звонок через два HFP-плеча с реальной проверкой микрофона и динамика. Если недоступно — PHONE_DIRECT остаётся гарантированным проектным резервом, не заявлять полный мост рабочим.
5. **AP/Web:** Android подключается к `192.168.47.1` без интернета, видит фактические статусы и может менять режимы; при выключении AP/перезапуске веб-панели уже работающая переговорка сохраняется.
6. **Сосуществование RF:** AP + 1/2 HFP + USB Line-In; проверять потери речи, переподключения, нагрев, питание на месте и при экранировании телом, поворотах головы, движении.
7. **Идентичность:** 10 холодных/тёплых перезапусков и смены порядков инициализации USB — роли устройств и привязки сохраняются без `hciN`, bus/device и PipeWire ID.
8. **Безопасность:** неизвестный клиент AP не получает управление без аутентификации; PIN/PSK не попадают в диагностический экспорт; изменение режима без подтверждения потери микрофона запрещено.

**Приоритеты:** сначала работоспособность одного HFP на AW859A; затем две гарнитуры (при необходимости с USB-BT), после — SOLO_STEREO и AP/Web, затем ANDROID_MEDIA; полнофункциональный ANDROID_BRIDGE_CALL не блокирует MVP переговорки.

## 20. AW859A/UWE5622: стабилизация встроенного Wi-Fi и перенос на Armbian (новое в v1.3)

**Базовый источник исправлений пользователя:** https://github.com/Medvedolog/opiz3-wlan-backport (ветка `main`; код и набор патчей фиксировать по конкретному SHA перед переносом). Отправная точка для драйвера — https://github.com/armbian/uwe5622. Работы проводятся в отдельной ветке/пакете MedveTalkie, без изменений работающей карты OpenWrt и без замены работающих модулей ядра без резервного варианта загрузки.

### 20.1. Целевой сценарий

- **STA 5 ГГц по умолчанию:** Android раздаёт интернет, Orange Pi автоматически подключается к сохранённому SSID (если опция включена), интернет-радио получает поток; голосовой режим не зависит от наличия интернета. Фактическая работа STA 5 ГГц подтверждена владельцем *на OpenWrt*, а не на выбранном Armbian.
- **STA 2,4 ГГц — резерв:** только после сравнения качества SCO/eSCO при трафике. Без ограничения сетевого доступа при отсутствии HFP; при наличии переговорки приоритет имеет речь.
- **AP — явное включение с IPS-экрана:** `Сеть → Точка доступа → Включить`, генерация стойкого случайного WPA2-PSK, QR-код подключения в формате `WIFI:T:WPA;S:<SSID>;P:<пароль>;;` (экранировать специальные символы), показ IP и отдельного QR для URL панели, таймер автоматического выключения и опция удержания AP при стендовых испытаниях. Не отображать пароль/QR постоянно без действия пользователя. Пароль панели независим от PSK.
- **Веб-интерфейс доступен в STA:** локальный адрес, обнаруживаемый по mDNS при поддержке телефона; AP включать только при необходимости. На IPS показывать текущий IP, SSID, диапазон, качество и статус IP-соединения. AP+STA на одном AW859A не считать гарантированным и не требовать одновременно.
- **Состояния сети:** `OFF`, `STA_CONNECTING`, `STA_CONNECTED`, `AP_STARTING`, `AP_ACTIVE`, `ERROR`, `RECOVERING`; изменения через единую машину состояний и выбранный менеджер сети, с тайм-аутами, откатом и журналом.

### 20.2. Источники патчей и приоритет переносимости

В репозитории OpenWrt на `main` изучить серию `package/kernel/uwe5622/patches/` по функциям, **а не применять OpenWrt `.patch` механически** на другую версию ядра.

| Группа | Конкретные патчи из репозитория | Решение для Armbian |
|---|---|---|
| Предотвращение зависаний и повреждения памяти | `130` (GFP_ATOMIC/TX), `160` (ADDBA), `190` (границы массива ADDBA), `220` (SDIO unlock при ошибке) | Высокий приоритет; сравнить с текущим `armbian/uwe5622`, перенести только отсутствующее, собрать и провести стресс-тест |
| Жизненный цикл контроллера/восстановление | `250` (SDIO unregister Allwinner), `310` (ожидание disconnect), `320` (журнал жизненного цикла), `330` (loopcheck, защита от self-cancel) | Высокий приоритет; особое внимание к взаимодействию с Bluetooth частью AW859A и выгрузке модулей |
| Каналы, полоса, 5 ГГц | `180` (5 GHz / DS IE), `200` (границы ширины и каналов) | Проверять по режимам STA/AP отдельно; `180` относится прежде всего к формированию AP, не объявлять его доказанным исправлением STA |
| Удобная диагностика | `060` (`dump_station`), `090` (`get_channel`), `120`–`150`, `240`, `270`, debugfs-патчи | По выбору: частота, реальная ширина, события firmware, статистика и отсутствие фиктивных значений; ограничить частоту опроса, чтобы диагностика не мешала речи |
| OpenWrt-специфичное | `010`, `020`, `030`, `080`, `110`, схема `kmod-*`, uci, procd, LuCI, сборочный Kbuild/backports | Не переносить как есть; заменить на нативные API ядра, DKMS/пакет Armbian и systemd; отдельно сверить `cfg80211` и ABI |

**Инженерные ограничения:** проверить точный `uname -r`, конфигурацию ядра, исходный tree/headers, `vermagic`, состояние upstream-патчей и DTS (`mmc1`/SDIO, clocks, reset, питание) до компиляции. Модуль, собранный для OpenWrt 6.12, **не является совместимым бинарником** Armbian даже при совпадающем архитектурном ABI. Прошивка, инициализация Wi-Fi и Bluetooth и загрузка после старта должны согласовываться; нельзя ради починки Wi-Fi нарушить HCI/SCO. Не перезапускать весь комбо-модуль при активном разговоре без уведомления — это может оборвать Bluetooth.

### 20.3. Восстановление и диагностика

- Перенести идею `uwe5622-recover` как отдельный **проверенный для Armbian** recovery-путь, с детектированием firmware/SDIO timeout и ограничением числа попыток; не выполнять сброс SDIO вслепую при активных голосовых соединениях.
- Никаких бесконечных retry, циклов `rmmod/modprobe`, записи больших CP2-логов на microSD и блокирующих команд в обработчиках UI. Телеметрию/CP2-логи по умолчанию держать в RAM (`/run`/`/tmp`), ограничивать размер и исключать секреты SSID/PSK.
- Диагностическая панель: версия AW859A/UWE5622, источник и SHA драйвера, версия firmware, `wlan0`/фактическое имя интерфейса, STA/AP, 2,4/5 ГГц, канал, RSSI при наличии, переподключения, ошибки SDIO/firmware/CP assert, времена восстановления, число активных HFP/SCO и режим сосуществования. Привязка — к sysfs/драйверу и свойствам, не к временному номеру интерфейса.
- Умышленно не включать экспериментальные отладочные сборы и повышенную частоту диагностического опроса в штатном режиме поездки.

### 20.4. Критерии приёмки переноса

1. На оригинальном Armbian подтвердить базовое обнаружение Wi-Fi и Bluetooth и зафиксировать контрольный журнал **до** переноса патчей.
2. Собрать воспроизводимый отдельный DKMS/пакет/образ с зафиксированными источниками и минимальным набором переносимых исправлений. Сравнить с текущим деревом Armbian на дублирование патчей.
3. Повторить 10 холодных/тёплых загрузок, STA 5 ГГц и 2,4 ГГц, 30–60 минут интернет-радио, обрыв/возобновление точки доступа Android.
4. Проверить параллельную работу 1 HFP и затем 2 HFP (если железо позволяет), включая голос под нагрузкой Wi-Fi STA 5 ГГц; записать потери/обрывы/latency; сравнить с Wi-Fi OFF.
5. Испытать AP с IPS и QR: Android подключается, открывает панель, проходит авторизацию; при выключении AP и сбоях сети действующий интерком не теряет свой пользовательский профиль без явного предупреждения.
6. Моделировать отказ Wi-Fi и оценить восстановление, не повредив pairing database BlueZ и не разорвав действующий HFP там, где восстановление возможно без общего сброса комбо-чипа. Если общий reset неизбежен, указать ограничение и обеспечить автоматическое восстановление гарнитуры.
7. Успех OpenWrt-тестов **не приравнивать** к успеху на Armbian: вести отдельную матрицу по ядрам, firmware, патчам, BT и режимам Wi-Fi.

## 24. Architecture freeze — C11, isolated processes (v1.4)

**Decision:** native C11 on Armbian CLI; avoid Python/Go/Rust runtime dependencies in the deployed product. Build via CMake. Do not claim runtime/audio efficiency until measured.

- `medvetalkied` (core): desired state, asynchronous command dispatch, SQLite app configuration, event stream, CivetWeb HTTP/WebSocket API. HTTP errors must not block control operations, but a process crash still kills its co-located HTTP service; this limitation is accepted for the first prototype.
- `medvetalkie-bt` (Bluetooth): BlueZ D-Bus integration, controller discovery by stable identity rather than `hciN`, headset pairing, HFP/HSP connection readiness, audio profile transitions and retry policy.
- `medvetalkie-ui` (LVGL): SPI ST7789/HDMI simulator and GPIO input as independent restartable client; it must not own business logic.
- BlueZ, PipeWire and WirePlumber run independently; the core must never pass raw PCM through IPC/HTTP.
- `systemd` manages crash recovery. Each component reconnects to peers and reconciles actual observed state after restart; do not write a second watchdog supervisor in the core.
- Local messaging: AF_UNIX SOCK_STREAM, explicit length-prefixed UTF-8 JSON frames (<=64 KiB initial bound), protocol version 1, unique operation ID, command ack separate from final result, monotonic revision on state snapshots. Only authenticated local clients may issue mutations; protect socket paths and peer credentials. No secrets in events/logs.
- Store desired settings in SQLite (versioned migrations); actual hardware and session state is in RAM and re-read from BlueZ/PipeWire. Never duplicate Bluetooth bond keys or plaintext Wi-Fi credentials in SQLite.

### 24.1 Headset state machine

Each role `HEADSET_1` / `HEADSET_2` tracks its own controller binding and states:
`UNASSIGNED -> DISCONNECTED -> CONNECTING -> CONNECTED_NO_AUDIO -> PROFILE_PENDING -> HFP_READY | A2DP_READY`; auxiliary `RECOVERING` and `ERROR`.

- `CONNECTED_NO_AUDIO` does **not** count as duplex audio.
- `HFP_READY` is reached only once a usable microphone source and playback sink are visible and an SCO/eSCO transport is verified; control-plane connection alone is insufficient.
- Every transition carries reason, timestamp and monotonically increasing revision. Stale events from previous attempts are ignored.
- Disconnect initiates bounded exponential backoff with jitter, not rapid looping; a failed adapter is surfaced as DEGRADED.
- Bluetooth controller identity uses controller address and sysfs/udev physical path when needed. `hciN`, USB bus numbering and PipeWire numeric IDs are volatile.
- Pairing is an explicit, time-limited user-authorized flow; never auto-pair unknown devices.

### 24.2 Global modes and priorities

`INTERCOM` requires two HFP-ready roles and two concurrently usable SCO channels (on two controllers by default); if one path fails, present `DEGRADED` and do not advertise duplex success.
`SOLO_STEREO` selects A2DP playback for one headset, with its HFP microphone unavailable.
`ANDROID_MEDIA` uses Android A2DP source to Linux A2DP sink and forwards to headset A2DP, capability-gated and to be validated.
`ANDROID_BRIDGE_CALL` is experimental and needs Linux phone-side HFP HF plus headset-side HFP AG; do not equate it with generic A2DP transport.
`PHONE_DIRECT` relinquishes the selected headset to Android without unwanted reconnect attempts.
`RADIO` and `GAME` are audio-source overlays; radio and game mutually exclusive by default. Intercom conversation has highest priority. `PAIRING` and `WIFI_AP` are independent settings operations with user consent.

No UI switches a mode directly. It submits a command, receives accepted/rejected and an operation ID, and later the actual resulting state. If switching fails, retain/recover the last good route where possible and report explicit failure.

### 24.3 IPC and web API baseline

See `docs/IPC.md`. Local Unix socket is the source of truth for frontend processes; web REST/WebSocket adapts the **same** state commands and events. One owner for mutations is the core. Avoid synchronous RPC roundtrips from realtime audio threads. SQLite transactions and schema migrations must be tested.

### 24.4 Kernel, WLAN and field validation

Use stock Armbian headless first; record kernel version, `uname -a`, hardware identifiers and BlueZ/PipeWire versions. Study the `Medvedolog/opiz3-wlan-backport` patch set as upstream evidence, not as a drop-in Armbian patch stack. Wi-Fi STA 5 GHz under OpenWrt has been confirmed by the project owner; reproduce on Armbian. Benchmark SCO audio under idle/active STA, AP, and deliberate body shielding. AP enabled from local UI; show generated PSK in standard Wi-Fi QR; use separate authenticated web session. Never reset the entire combo chip as a routine WLAN recovery step if doing so would interrupt a critical Bluetooth connection.

### 24.5 First-deliverable acceptance

1. Three C11 binaries build reproducibly and report version.
2. Core/BT/UI IPC schema and state transitions unit-tested before live hardware integration.
3. Single HFP headset is actually verified with audio both ways.
4. Dual headset full-duplex is verified on real Orange Pi Zero 3; only then mark intercom as working.
5. Web settings and HDMI emulator developed independently of SPI arrival.
6. Power measurements logged externally using a USB 5 V power meter, with experimental CPU governors and limits.


## 25. Web Alpha, USB identity and observability (2026-11-12 amendment)

This section is normative for the first web/control implementation; unimplemented features must remain marked as planned. Existing dual-HFP acceptance gates remain unchanged.

### 25.1 Priorities and boundaries

P0: safe inventory of hardware, stable logical bindings, lifecycle/reconnect reporting and read-only diagnostics. P1: authenticated CivetWeb status/configuration UI, BlueZ D-Bus controller/headset management and asynchronous operations. P1: PipeWire/WirePlumber route tests for ATS Mini V4 analog audio via USB input to an A2DP helmet headset, followed by test speech mixing and ducking. P2: Wi-Fi STA/AP setup after coexistence validation with AW859A/UWE5622. SPI LVGL display is deferred; it consumes the same state/event model as WebUI. No fabricated functional HFP, GATT or radio controls.

### 25.2 USB and Bluetooth stable identity

- Never persist USB Bus/Device numbers, /dev/sdX, ALSA card indices, PipeWire numeric node IDs or hciN as device identity; they are volatile after reboot and hotplug.
- Inventory devices from sysfs/udev: VID/PID, manufacturer/product, optional serial, USB interface and driver, physical-port topology, and (for Bluetooth controllers) controller address. Treat all reported attributes as evidence, not proof of unique identity.
- Maintain logical roles HEADSET_A, HEADSET_B, BT_CONTROLLER_A/B, RADIO_AUDIO and RADIO_CONTROL independently of runtime enumeration.
- Match using verified unique serial or controller address where available. Detect duplicate or absent serial numbers. For indistinguishable devices, a previously user-confirmed physical-port binding may be used; moving such a device to another indistinguishable port requires explicit reassignment. Never silently swap two active HFP roles.
- Device match outcomes: MATCHED, MISSING, AMBIGUOUS, CHANGED. Do not automatically pair unknown headsets, overwrite bonds or reuse another controller's pairing keys.
- Monitor udev add/remove/change and reconcile desired against observed state with bounded exponential backoff and jitter. On removal, mark only affected routes DEGRADED; never restart the whole core to cure a peripheral failure.
- Track USB enumeration changes over reboots, device resets, adapter disappearance, controller and headset reconnect counts and route restoration time.

### 25.3 System and Bluetooth diagnostics

- Web diagnostics pages: system (board/revision, Armbian/kernel, service versions, uptime, temperature), memory (MemAvailable, total and per-service RSS/CPU), networking (interface, MAC, IP, Wi-Fi mode/SSID/RSSI if available), USB tree (equivalent to lsusb -t plus errors), Bluetooth (controller stable ID/current hciN, associated headset, profile/codec, actual battery data), event log and health.
- Surface D-Bus/BlueZ, kernel USB/HCI, PipeWire/WirePlumber and systemd service failures with timestamp, affected logical device, event type, recovery attempts and outcome. Keep bounded history and a downloadable scrubbed diagnostic bundle (no Wi-Fi passwords, pairing keys or secrets).
- Bluetooth link RSSI in dBm is optional and capability-dependent; an unavailable or stale reading is UNKNOWN, never invented. Reconnect/dropout trends and flapping warnings must still work without RSSI. Initial configurable flapping rule: 5 disconnects in 60 seconds, with hysteresis/cooldown.
- WebSocket pushes events; metrics are sampled conservatively (initially no faster than one sample per 2 s while diagnostics are open) to avoid disturbing SCO/A2DP and the 1 GB system. Diagnostic collection cannot block the audio realtime path.

### 25.4 Mobile WebUI and control API

- Authenticated pages: Overview, Headsets/Intercom, Radio (ATS Mini and internet radio sources), Network (STA/AP), Hardware and Diagnostics, Settings. The WebUI is usable over wired LAN or Wi-Fi STA before AP coexistence is proven.
- Core exposes versioned asynchronous, permission-checked control commands with operation IDs; snapshots/events are shared by web and later LVGL over the existing versioned IPC model.
- API baseline: GET /api/v1/status; GET /api/v1/bt/devices; POST /api/v1/bt/scan; POST /api/v1/bt/pair; PUT /api/v1/bt/roles; GET /api/v1/wifi/networks; POST /api/v1/wifi/connect; GET /api/v1/radio/state; GET /api/v1/radio/presets; POST /api/v1/radio/tune; GET /api/v1/diagnostics/{system,processes,usb,bluetooth,network,events,health}; POST /api/v1/devices/rescan. These paths specify the target design, not existing handlers.
- ATS Mini presets reside on Orange Pi even when the detachable receiver is missing. Saved desired presets and receiver-observed state are distinct; reconnecting must not blindly overwrite manual radio tuning.

### 25.5 Acceptance tests

1. Across at least five cold boots, previously distinguishable USB devices retain correct logical roles despite changed bus/device, ALSA, PipeWire or hci indices.
2. Disconnect/reconnect each USB Bluetooth adapter and the USB audio input during operation; unrelated components stay functional, affected routes report DEGRADED then recover if hardware permits.
3. Attach two identical adapters with missing/duplicate serials; ambiguous mapping never silently swaps headset roles. Confirmed physical port assignments survive repeated boots, and moves are flagged.
4. Trigger at least five disconnects within 60 s; web reports FLAPPING, counters, last error and recoveries, without aggressive retry loops.
5. Compare system diagnostics with actual /proc, sysfs, BlueZ and journal state; unsupported RSSI, battery, codec or sensor metrics show UNKNOWN.
6. Verify authenticated WebUI and diagnostic-export sanitization. Check CPU/RSS of all services and no audio dropout attributable to diagnostic refresh.
7. Verify ATS Mini analog input -> PipeWire -> one A2DP headset, then speech-file mix and smooth radio ducking; record BLE GATT control separately as unverified until tested.
